# Маркетинговый лендинг и блог

## Обзор

`apps/web` обслуживает две совсем разные вещи из одного SvelteKit-приложения: аутентифицированное клиент-рендеренное SPA (всё под `(app)` и `(auth)`) и публичный, ориентированный на поисковики маркетинговый сайт — лендинг на трёх языках плюс многоязычный блог. Маркетинговый сайт пререндерится в чистый HTML **вообще без JavaScript-бандла**, потому что весь смысл в том, чтобы Google, Bing и LLM-краулеры видели настоящий текст, ничего не выполняя.

Реализовано в рамках issue [#206](https://github.com/micode-ai/marketing-ai-assistant/issues/206), десятью задачами. `docs/eng/13-marketing-landing-and-blog.md` — англоязычная версия этого документа.

**Публичные URL:**

| URL | Содержимое |
|---|---|
| `/` | Лендинг на английском |
| `/pl/` | Лендинг на польском |
| `/ru/` | Лендинг на русском |
| `/blog/` | Выбор языка (noindex) |
| `/blog/<lang>/` | Индекс блога для этого языка |

| `/llms-full.txt` | Весь корпус (копирайтинг лендинга + тело каждой статьи) для AI-краулеров |

Раньше `/` редиректил в аутентифицированное приложение; теперь нет. Это настоящая, индексируемая страница.

## Группа роутов `(marketing)`

Корневой `apps/web/src/routes/+layout.ts` задаёт значения по умолчанию для всего приложения:

```ts
export const ssr = false;
export const prerender = false;
```

`csr` там не задан, поэтому остаётся значением по умолчанию SvelteKit — `true`. Эта комбинация — нет SSR, есть CSR, нет prerender — это ровно то, что нужно SPA с JWT-защитой: серверу нет смысла что-либо рендерить для аутентифицированной страницы, поскольку у обычного fetch нет сессии, привязанной к куке, для гидратации.

`apps/web/src/routes/(marketing)/+layout.ts` переопределяет все три опции плюс `trailingSlash` для каждого роута внутри группы:

```ts
export const ssr = true;
export const prerender = true;
export const csr = false;
export const trailingSlash = 'always';
```

Именно `csr = false` убирает JavaScript-бандл — `ssr`/`prerender` управляют *когда* генерируется HTML (во время сборки или во время запроса), но без `csr = false` SvelteKit всё равно отдаёт код гидратации и роутер для страницы. На маркетинговой странице нет интерактивности, которой нужен роутер: каждая ссылка — обычный `<a href>`, форм нет, а единственная причина отправлять JS была бы в том, чтобы получить ровно тот же HTML, который уже произвёл prerendering. `csr = false` — это то, что делает возможным артефактное доказательство ниже (ноль `_app/immutable/*.js`).

`trailingSlash = 'always'` держит каждый маркетинговый URL — лендинги, индексы блога, статьи — каноничным с завершающим слэшем, что совпадает с тем, что уже предполагают `links.ts` (`landingPath`, `blogIndexPath`, `articlePath`) и билдеры sitemap/hreflang.

Ни у `(app)`, ни у `(auth)` нет своего `+layout.ts`, поэтому обе группы наследуют корневые `ssr=false, prerender=false, csr=true` без изменений.

### `prerender = 'auto'` у роута статьи

Каждый роут в группе — `prerender = true` по наследованию от layout группы, **кроме** `blog/[lang=blang]/[slug]/+page.ts`, где `prerender = 'auto'` задан явно:

```ts
// 'auto' (не привычный для группы принудительный `true`): пока markdown-файлов нет,
// entries() ниже возвращает пусто, и роут никогда не обходится — это SvelteKit'овская
// handleUnseenRoutes по умолчанию считает ошибкой сборки для роута с принудительным
// `true`. 'auto' всё равно пререндерит каждую запись, которую генерирует этот список,
// когда статьи появляются — он лишь снимает ошибку «этот роут произвёл ноль страниц»
// для промежуточного состояния, когда их ещё нет.
export const prerender = 'auto';
```

Это имеет значение только для гипотетического состояния, когда `ARTICLES` пуст — с девятью реально опубликованными статьями `entries()` всегда возвращает девять пар `{lang, slug}`, и каждая из них пререндерится в статический файл, точно так же, как если бы роут был принудительно `true`. Не читайте `'auto'` как «иногда пререндерится, иногда нет» — он пререндерит всё, что называет `entries()`; он лишь ослабляет проверку для крайнего случая с нулём записей.

### Статический файл побеждает роут с тем же путём

`apps/web/static/` отдаётся как есть, и SvelteKit резолвит статический файл раньше, чем роут с тем же путём. В начале этой работы `apps/web/static/sitemap.xml` существовал (заглушка) одновременно с роутом `sitemap.xml/+server.ts` — статический файл всегда побеждал, и вычисленный во время сборки sitemap эндпоинта был незаметно недостижим. Статический файл удалили; теперь единственный источник `/sitemap.xml` — это роут. Если добавленный вами роут под `(marketing)` ведёт себя так, будто вообще не выполняется, сначала проверьте `apps/web/static/` на файл с тем же путём.

## Копирайтинг лендинга: обычные объекты, а не `svelte-i18n`

Остальная часть приложения использует `svelte-i18n`: файлы локали лениво загружаются в браузере, стор инициализируется после `onMount`, а страницы показывают состояние загрузки, пока он не разрешится (см. [Интернационализация](09-internationalization.md) и раздел про `I18nGate` ниже). Для CSR-приложения это нормально — там всегда есть работающий JavaScript, чтобы загрузить локаль.

У маркетинговых страниц `csr = false`. Если бы они шли через `svelte-i18n`, пререндеренный HTML вообще не содержал бы переведённого текста — локаль разрешалась бы только в браузере, и краулер (или реальный посетитель с медленным JS) увидел бы либо ничего, либо скелетон загрузки. Поэтому копирайтинг лендинга — это обычные, статически импортируемые TypeScript-объекты:

```
apps/web/src/lib/marketing/copy/
  types.ts   — интерфейс LandingCopy (форма, которой должен соответствовать каждый язык)
  en.ts      — англоязычный словарь
  pl.ts      — польский словарь
  ru.ts      — русский словарь
  index.ts   — COPY: Record<Lang, LandingCopy>, copyFor(lang)
  copy.test.ts
```

Поскольку `copyFor(lang)` вызывается во время серверного рендеринга (пререндеринг *и есть* серверный рендеринг, просто выполненный один раз во время сборки и закэшированный в файл), возвращённые строки уже запечены в HTML — никакого клиентского поиска, никакой вспышки непереведённого контента, никакого состояния загрузки.

`copy.test.ts` следит, чтобы это оставалось верным для всех трёх языков:

- **Одинаковая структура ключей.** `keyPaths(COPY.en)` сравнивается с `keyPaths(COPY.pl)` и `keyPaths(COPY.ru)` — если ключ есть в одном языке и отсутствует в другом (в том числе внутри массива, например пропущенный пункт FAQ), тест падает и называет, какой язык отличается.
- **Нет пустых строк.** Каждое листовое значение должно быть непустой, не-пробельной строкой.
- **Длина meta-описания.** `meta.description` должно быть ≤ 155 символов на каждом языке (поисковики обрезают сниппеты дальше этого).
- **Ровно шесть пунктов FAQ** на язык, потому что блок FAQ питает JSON-LD `FAQPage`, и несовпадающее количество было бы контентной ошибкой, а не технической.

Если вы добавляете новый ключ в `LandingCopy` в `types.ts`, его нужно добавить в `en.ts`, `pl.ts` и `ru.ts` в том же PR — иначе тест специально упадёт.

## Статьи

### Где они лежат и как устроена модель

```
apps/web/src/content/blog/en/*.md
apps/web/src/content/blog/pl/*.md
apps/web/src/content/blog/ru/*.md
```

Каждый файл — это frontmatter + тело в Markdown. `apps/web/src/lib/marketing/content/index.ts` загружает их все во время сборки/dev-режима через `import.meta.glob('/src/content/blog/**/*.md', { query: '?raw', import: 'default', eager: true })` и сразу прогоняет через `buildArticles()` из `content/articles.ts`. `buildArticles` бросает исключение при нарушении любого инварианта, и поскольку `ARTICLES` вычисляется на уровне модуля, **это исключение происходит во время сборки/загрузки модуля Vite** — сломанная статья валит всю сборку (или роняет запуск dev-сервера), а не тихо производит битую страницу.

`content/frontmatter.ts` — намеренно минимальный ридер frontmatter, а не YAML-библиотека, потому что статьи используют ровно три формы:

```yaml
---
slug: ai-social-media-content
lang: en
pair: ai-social-content
title: How to generate social media content with AI without sounding like a robot
description: Одно предложение-summary, ≤155 символов.
date: 2026-09-10
updated: 2026-09-10
tags: [content, social media, ai]
faq:
  - q: Can AI write social media posts that sound human?
    a: AI writes social posts that sound human when it is given the brand voice, the audience and real product details.
  - q: How much editing does an AI draft need?
    a: An AI draft usually needs its opening line and call to action rewritten by hand.
---

Тело в Markdown начинается здесь. `## Заголовки`, таблицы, списки — всё, что поддерживает `marked`.
```

- Скалярные пары `ключ: значение`, значения опционально в кавычках (`'одинарных'` или `"двойных"` — снимаются только когда открывающая и закрывающая кавычка совпадают, поэтому `Marketers'` не обрезается наполовину).
- Инлайн-массивы: `tags: [content, planning]`.
- Один список `faq:` из пар `- q: ...` / `a: ...` (используется для секции FAQ на странице статьи и узла JSON-LD `FAQPage`).

Результат парсинга становится `Article`:

```ts
interface Article {
  slug: string;
  lang: Lang;           // 'en' | 'pl' | 'ru'
  pair: string;          // связывает эту статью с её переводами
  title: string;
  description: string;
  date: string;           // ISO, дата первой публикации
  updated: string;         // ISO, дата последнего изменения — по умолчанию равна `date`, если не указана
  tags: string[];
  faq: FaqEntry[];
  html: string;            // отрендерено из тела Markdown через `marked`
  readingMinutes: number;  // Math.max(1, round(число слов / 200))
}
```

`content/index.ts` также экспортирует `RAW_BODIES` — тот же glob, ключ `${lang}/${slug}`, содержит *непарсенное* тело Markdown. `/llms-full.txt` использует именно его вместо `Article.html`, чтобы AI-краулеры получали исходный Markdown, а не очищенный/отрендеренный HTML.

### Инварианты, которые валят сборку

`toArticle()` и две межфайловые проверки в `buildArticles()` бросают `Error` с именем проблемного файла (а для двух проверок на дубликаты — обоих конфликтующих файлов). Вот те, с которыми вы реально столкнётесь:

| Правило | Сообщение об ошибке содержит |
|---|---|
| `slug`, `lang`, `pair`, `title`, `description`, `date` отсутствует или пусто | `frontmatter key "<key>" is missing or empty` |
| `lang` не равен `en`/`pl`/`ru` | `unknown language "<lang>"` |
| `slug` содержит что-то, кроме строчных букв, цифр, дефисов | `slug "<slug>" must be lowercase letters, digits and hyphens only` |
| `description` длиннее 155 символов | `description is <n> characters, the limit is 155` |
| `date` или `updated` не в формате `YYYY-MM-DD` / не реальная дата | `<key> "<value>" is not an ISO date` |
| `updated` раньше, чем `date` | `updated (<u>) is earlier than date (<d>)` |
| Два файла на одном языке переиспользуют `slug` | `duplicate slug "<slug>" in language "<lang>": <path1> and <path2>` |
| Два файла на одном языке делят один `pair` | `pair "<pair>" has more than one "<lang>" article: <path1> and <path2>` |

Ограничение на символы в slug существует потому, что slug попадает и в URL, и — неэкранированным — в сгенерированный sitemap XML: `&` или `<` в slug произвели бы невалидный XML.

Ничего из этого не ловится TypeScript'ом — это целиком рантайм-валидация реальных Markdown-файлов, поэтому `articles.test.ts` прогоняет каждый из этих путей напрямую против `buildArticles()`, а `real-content.test.ts` проверяет факты про *реально* опубликованный контент (девять статей, по три на язык, каждый `pair` переведён на все три языка, взаимный hreflang, у каждой статьи минимум три пункта FAQ).

### Как добавить статью

1. **Выберите slug для `pair`.** Если это новая тема — придумайте свой (короткий, kebab-case, стабильный — пользователю он никогда не показывается, используется только для связи переводов). Если вы добавляете недостающий перевод существующей статьи — переиспользуйте её `pair` без изменений.
2. **Сначала напишите английский файл** (или тот язык, что есть): `apps/web/src/content/blog/en/NN-your-slug.md` — префикс `NN-` нужен только для читаемого листинга файлов, парсер его не читает. Заполните `slug`, `lang`, `pair`, `title`, `description` (≤155 символов), `date`, `updated`, `tags` и минимум три пары FAQ — `real-content.test.ts` требует ≥3 на статью (правило «шесть на язык» из `copy.test.ts` относится только к копирайтингу лендинга и на статьи не распространяется). У всех опубликованных статей ровно по три.
3. **Переведите на два оставшихся языка**, по одному файлу в `content/blog/pl/` и `content/blog/ru/`, с **тем же `pair`** и slug, подходящим языку. `pairSlugs()` / `articleAlternates()` строят hreflang из тех slug'ов, что делят один `pair` — если забыть перевод, этот язык просто выпадет из alternates (без ошибки), но проверка «переводит каждую статью на все три языка» из `real-content.test.ts` упадёт, как только ваш новый `pair` окажется в корпусе, потому что она проверяет, что у каждого `pair` есть все три языка.
4. **Запустите тесты:**
   ```bash
   cd apps/web && corepack pnpm exec vitest run
   ```
   `articles.test.ts` проверяет логику парсера/билдера изолированно; `real-content.test.ts` и `copy.test.ts` проверяют именно те файлы, что вы только что добавили. Опечатка в ключе frontmatter, описание длиннее 155 символов, несовпадение `date`/`updated`, дублирующийся slug или пропущенный перевод — всё это упадёт здесь, ещё до сборки.
5. **Соберите и проверьте артефакт:**
   ```bash
   corepack pnpm --filter @marketing-ai/web build
   ```
   Убедитесь, что ваша статья появилась в `apps/web/.svelte-kit/output/prerendered/pages/blog/<lang>/<slug>/index.html`, и что `/sitemap.xml` и `/llms.txt` в том же выводе её подхватили (см. «Как проверить пререндеренный вывод» ниже).

Вам не нужно трогать ни один файл роута, билдер sitemap или эндпоинты `llms.txt`/`llms-full.txt` — все они берут список статей из `ARTICLES` / `articlesFor()` и подхватывают новые файлы автоматически, если соблюдены перечисленные выше инварианты.

## SEO

`apps/web/src/lib/marketing/Seo.svelte` — единственное место, которое пишет в `<svelte:head>` для каждой маркетинговой страницы: `<title>`, meta description, canonical-ссылка, `robots` (index или `noindex,follow` для выбора языка блога), hreflang-alternates, теги Open Graph (включая `og:locale:alternate` для остальных языков), теги Twitter card и блок `<script>` с JSON-LD, если он передан.

**hreflang** (`seo/alternates.ts`) — `landingAlternates()`, `blogIndexAlternates()` и `articleAlternates(slugs)` каждая возвращает все языки, которые реально есть у конкретной страницы, плюс запись `x-default`, указывающую на английский URL (пропускается только `articleAlternates`, когда у пары нет английского перевода). Это намеренно управляется данными из `pairSlugs()`, а не предполагает, что все три языка есть всегда, потому что `articleAlternates` используется для каждой статьи отдельно, и перевод в принципе может отсутствовать.

**JSON-LD** (`seo/jsonld.ts`) — каждая страница строит один `@graph` через `jsonLdScript([...nodes])`, экранируя каждый `<` в `\u003c`, чтобы буквальный `</script>` внутри любого поля (например, ответа FAQ) не мог вырваться из тега script. Используемые узлы:

- `organizationNode()` — на каждой странице; несёт `@id`, чтобы другие узлы могли ссылаться на него через `author`/`publisher`, не повторяя его. `sameAs` добавляется только если `SOCIALS` (в `links.ts`) непусто — см. «Что намеренно отсутствует» ниже.
- `websiteNode()`, `softwareApplicationNode()`, `faqNode()` — только на страницах лендинга.
- `breadcrumbNode()` — на индексе блога и страницах статей.
- `articleNode()` — только на страницах статей; несёт и `datePublished`/`dateModified`, и указатели `author`/`publisher` обратно на узел организации.

Узел организации должен путешествовать с каждым графом, который ссылается на него через `@id` — граф с `articleNode()`, но без `organizationNode()`, имел бы `author: {"@id": "…/#organization"}`, указывающий в никуда. Каждая страница, которая строит граф, включает `organizationNode()` первым по этой причине (см. паттерн `$: jsonLd = jsonLdScript([organizationNode(), ...])` в `Landing.svelte` и обоих компонентах страниц блога).

**Что намеренно отсутствует:** ни `offers`, ни `aggregateRating` в узле `SoftwareApplication` (нет цены, которую можно было бы рекламировать, и нет данных отзывов, на которых можно было бы основать рейтинг — придумывать любое из этого было бы спамом в структурированных данных), и никаких выдуманных профилей в соцсетях в `sameAs` (`SOCIALS` в `links.ts` — пустой массив с комментарием, объясняющим почему: «выдуманный профиль в `sameAs` хуже, чем отсутствие `sameAs` вообще»). `jsonld.test.ts` закрепляет оба этих факта («никогда не рекламирует цену или рейтинг»).

## Sitemap, `llms.txt`, `llms-full.txt` и `robots.txt`

Все три текстовых эндпоинта лежат под `(marketing)` как файлы `+server.ts` с `export const prerender = true`, и все используют хелпер SvelteKit `text()`, а не `new Response(...)` — в ESLint-конфиге репозитория не настроен глобал `Response`, поэтому сырой `new Response()` там был бы ошибкой линтера.

**`/sitemap.xml`** (`seo/sitemap.ts`) перечисляет каждый индексируемый URL: три страницы лендинга, три индекса блога и каждую статью, у каждой — свой `<lastmod>`. *Индекс* блога использует самую свежую дату `updated` среди статей этого языка (по умолчанию — «сегодня», если статей ещё нет); статья использует свою собственную `updated`. `/blog/` — выбор языка с noindex — намеренно отсутствует в sitemap: перечислять страницу, которую вы же велите роботам не индексировать, было бы противоречием.

**`/llms.txt`** — короткая структурированная сводка в Markdown, нацеленная на AI-краулеров: описание сайта, ссылки на все три лендинга, и ссылка + однострочное описание для каждой статьи на каждом языке. Задумана для полного прочтения чем-то, что строит представление о сайте, а не для людей, листающих страницы.

**`/llms-full.txt`** — та же идея, доведённая дальше: для каждого языка — весь копирайтинг лендинга (hero, features, how-it-works, FAQ), за которым следует *исходное тело Markdown* каждой статьи (из `RAW_BODIES`, а не отрендеренный HTML), всё сконкатенировано. Это эндпоинт «отдать языковой модели весь корпус целиком».

**`robots.txt`** (статический файл в `apps/web/static/robots.txt`, не роут) запрещает каждый путь аутентифицированного приложения (`/dashboard`, `/projects`, `/settings`, …) и внутренние страницы авторизации (`/auth/`, `/forgot-password`), явно разрешает `/blog/` и указывает на `/sitemap.xml`. Явный `Allow: /` для страниц лендинга не нужен — правила disallow — единственное, что убирает доступ, разрешённый по умолчанию, а ни одно из них не касается `/`, `/pl/` или `/ru/`. JS/CSS под `/_app/` намеренно *не* блокируются, потому что Googlebot должен их получить, чтобы отрендерить страницы аутентифицированного приложения, которые *разрешены* — но у маркетинговых страниц вообще нет `/_app/*.js`, который нужно было бы получать (см. ниже).

## Перенос гейта i18n

До этой работы `apps/web/src/routes/+layout.svelte` (корневой layout, применявшийся к *каждому* роуту, включая маркетинговую группу) вызывал `setupI18n()` и `waitLocale()` из `svelte-i18n` и блокировал рендеринг спиннером, пока локаль не разрешится. Это ровно то поведение, работающее только на клиенте, которого маркетинговым страницам нужно было избежать.

Сам гейт, `$lib/i18n/I18nGate.svelte`, не изменился — он по-прежнему делает `onMount(async () => { await setupI18n(); await waitLocale(); ready = true })` и рендерит спиннер, пока не наступит `ready`. Изменилось *место его применения*: он переехал из корневого layout в `(app)/+layout.svelte` и `(auth)/+layout.svelte` по отдельности. Корневой layout (`+layout.svelte`) больше вообще на него не ссылается — теперь именно `(marketing)` ничего не наследует от гейта, который без JavaScript никогда бы не разрешился. `(app)` и `(auth)` по-прежнему блокируются на нём точно так же, как раньше; в i18n-поведении аутентифицированного приложения ничего не изменилось — это проверено открытием `/login` с включённым JavaScript и подтверждением, что каждая надпись переведена (а не сырые ключи вроде `auth.login.title`), а не бесконечным показом спиннера гейта.

## `<html lang>`

В `apps/web/src/app.html` есть `<html lang="%lang%">` — `%lang%` не входит в собственные плейсхолдеры SvelteKit `%sveltekit.*%`, поэтому подставляется вручную в `apps/web/src/hooks.server.ts`:

```ts
return resolve(event, {
  transformPageChunk: ({ html }) => html.replace('%lang%', langFromPath(event.url.pathname)),
});
```

`langFromPath()` (`lib/marketing/lang-from-path.ts`) читает язык прямо из URL — первый сегмент пути, или второй, если первый — `blog` — по умолчанию `en` для всего, что не распознано (включая каждый роут аутентифицированного приложения, и это намеренно: само приложение — англоязычная оболочка, где текст внутри страниц обрабатывает `svelte-i18n`, поэтому его `<html lang>` остаётся `en`). Это выполняется и во время пререндеринга, поэтому у каждой пререндеренной страницы правильный атрибут `lang` запечён сразу, а не оставлен таким, каким его произвёл бы неизменённый `app.html`.

## Как проверить пререндеренный вывод

После `corepack pnpm --filter @marketing-ai/web build` маркетинговые страницы оказываются в `apps/web/.svelte-kit/output/prerendered/pages/`: `index.html`, `pl/index.html`, `ru/index.html`, `blog/index.html`, `blog/<lang>/index.html` для каждого языка, `blog/<lang>/<slug>/index.html` для каждой статьи, плюс `sitemap.xml`, `llms.txt` и `llms-full.txt` как обычные файлы (всего 19 файлов для опубликованных 3 лендингов + 1 выбора языка + 3 индексов блога + 9 статей + 3 текстовых эндпоинтов).

Важное свойство — **ноль** `_app/immutable/*.js` и **ноль** `modulepreload` во всей этой директории: именно это доказывает, что `csr = false` реально убрал бандл, а не просто его спрятал. Одна ссылка `_app/immutable/*.css` на страницу — это ожидаемо и правильно (страницы по-прежнему стилизованы Tailwind'ом — пропадает только JS):

```bash
cd apps/web/.svelte-kit/output/prerendered/pages
grep -rhoE '_app/immutable/[^"'"'"']*\.js' . | wc -l   # ожидается 0
grep -rho 'modulepreload' . | wc -l                     # ожидается 0
grep -rhoE '_app/immutable/[^"'"'"']*\.css' . | sort -u # ожидается ровно один общий файл
```

Также стоит выборочно проверять после любого изменения в этой области: `<html lang="...">` совпадает с языком страницы, hreflang-alternates на `/` указывают на все три языка плюс `x-default`, а `/sitemap.xml` / `/llms.txt` содержат статью, которую вы только что добавили или изменили.

Для полной ручной проверки запустите `corepack pnpm --filter @marketing-ai/web dev` и откройте `/`, `/pl/`, `/ru/`, `/blog/en/`, одну статью, `/blog/` и `/login` — маркетинговые страницы должны отрендериться полностью, а `/login` должна показывать переведённые надписи (подтверждая, что перенос гейта i18n не сломал i18n аутентифицированного приложения).
